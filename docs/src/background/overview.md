# [Package Overview](@id overview)

This page sketches the two pillars of `EnergyModelsGasNetworks`: gas transport based on flow-pressure relationship and quality-tracking pooling.

The detailed documentation on the methodology behind `EnergyModelsGasNetworks` can be found in [Theoretical Background](@ref method).

## [Flow–pressure coupling](@id overview-flow)

- **Potentials on nodes and links.** Defining resources of type `ResourcePressure` activates the flow-pressure constraints (see [Internal Constraints](@ref lib-int-fun-con)) on nodes and links. Potentials can be bounded with [`FixPressureData`](@ref), [`MaxPressureData`](@ref), or [`MinPressureData`](@ref).
- **Weymouth relationship.** For single-component flows, the pressure-flow curve is linearised with the first-order Taylor. The defined cuts will be defined between the minimum and maximum inlet pressures stored in [`PressureLinkData`](@ref). For blended gases, the non-convex surface is outer-approximated with planes generated by [PiecewiseAffineApprox](https://github.com/sintefore/PiecewiseAffineApprox.jl).
- **Optimiser** The PWA planes require a MIP-capable solver; set it with [`set_optimizer_pwa!`](@ref) (e.g., HiGHS, Xpress, Gurobi) before building the model. The discretisation step of the pressure grid for the approximations can be tuned via [`set_step_pressure!`](@ref).
- **Binary variables.** One binary array — `has_flow` — is declared per pressure-carrying link per time period. `has_flow` enables big-M deactivation of idle links in pressure-balance and capacity constraints; when active (`has_flow=1`), both the upper and lower bounds on `potential_in[n]` bind, forcing equality with the link outlet potential. The array is restricted to links carrying at least one `CompoundResource`; Power-only links are excluded.

## [Pooling and quality tracking](@id overview-pool)

- **Pooling formulation.** Defining a resource of type [`ResourcePooling`](@ref) stores a blended resource and its subresources. Subresources can be of type `ResourceCarrier` or `ResourcePressure`. The former activates only the pooling formulation, the latter the pooling formuation and flow-pressure constraints. 
- **Quality limits.** [`RefBlendData`](@ref) (for nodes) and [`BlendLinkData`](@ref) (for links) subtypes specify maximum and minimum qualities for subresource at nodes or links. Quality is enforced at pooling nodes and sinks, and component proportions are tracked so they can be reused by the pressure formulation of blended gases.
- **Node types for blending.** Three node types handle mixing of blend subresources:
  - [`PoolingNode`](@ref) — for junctions with **≥ 2 outgoing** blend links. Uses the standard bilinear pooling formulation (`proportion_out × total_flow = component_flow`) to ensure all splits share the same composition.
  - [`BlendingNode`](@ref) — for junctions with **exactly 1 outgoing** blend link. Uses a **linear** formulation: component mass balance directly determines the output composition without `proportion_out` variables or bilinear constraints. Quality bounds (`max_h2 × total_flow`) remain linear because the quality limits are fixed parameters. Preferred over `PoolingNode` whenever the topology allows it — typically pre-sink, post-source, and single-path transit mixing nodes.
  - [`TransitNode`](@ref) — for pass-through junctions with no injection or extraction and no quality enforcement. The composition is copied linearly from upstream, so a `TransitNode` sends blend down **at most one outgoing link per period** (`Σ has_flow[l_out, t] ≤ 1`). Bidirectional pipelines are supported, since only one direction is active. With several outgoing blend links, every one of them must carry a pressure resource (so that it has a `has_flow` binary); otherwise `validate_blend_topology` raises an `ArgumentError`. Use `PoolingNode` or `DiscretizedPoolingNode` where the blend must split into several pipes at the same time.
